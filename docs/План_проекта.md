# План проекта «Weather Forecast AI»

**Тема:** Прогноз погоды (температура, осадки) — интеллектуальная система прогнозирования
временных рядов с мультиагентной архитектурой, Agentic RAG и оценкой качества.

- **Саттарова Аделина** — бэкенд и DevOps (далее **А**).

**Исходные материалы** (лежат вне репозитория, у команды локально):

- методички Этапов 1–12 (Step_1–Step_12, ноутбуки курса) — технический how-to; написаны

## 1. Цель и результат

Пользователь загружает метеоряд (или выбирает встроенный датасет), указывает город, целевую
переменную (`mean_temp` | `precipitation`) и горизонт 7–14 дней. Система через агентный цикл
подбирает модель (Tool Calling), строит прогноз, валидирует его физическую реалистичность
(климатические пределы) и возвращает результат с метриками MAE/RMSE/MAPE/MASE/WAPE
и сравнением с наивным прогнозом.

**Сдача:** репозиторий (local + prod конфигурации), README, скрипты генерации/импорта базы знаний,
`run_eval.py` (режимы, подвыборки, агентные метрики, стат. тесты), отчёт с анализом, UI, Docker.

**Критерии оценки (из задания):** архитектура и Tool Calling — 25%, функциональность и RAG — 25%,
оценка качества — 15%, тестирование и CI — 15%, документация — 10%, инфраструктура — 10%.
Бонусы — до +20% (см. раздел 7).

---

## 2. Архитектура (кратко)

Пайплайн: `Supervisor → DataAnalyst → ModelSelector → обучение/инференс → Validator → Critic
→ (Editor) → результат`, цикл до 3 итераций, HITL при несходимости/экстремумах.

- **State** (`backend/core/models.py::ForecastState`, Pydantic) — передаётся между агентами
  только по ссылке (ID в БД); погодная специфика в `metadata` (`city`, `target_variable`,
  `climate_bounds`, `extreme_flags`).
- **Tool Calling**: реестр `fit_arima / fit_prophet / fit_xgboost / fit_tabular_xgboost`
  (+ бонус `infer_chronos`); fallback — 3 попытки, затем SARIMA (`auto_arima`).
- **RAG**: BM25 + Qdrant/FAISS + RRF; фичи ряда (тренд/сезонность/энтропия/ACF) + PCA до 128 dims.
- **База знаний**: ≥1000 кейсов «ряд → лучшая модель + гиперпараметры + метрики + описание»,
  справочник ≥500 метеотерминов.
- **Observability**: `reasoning_logs` (иерархия, `parent_id`) + `llm_calls` (токены, latency).
- Структура папок соответствует заданию (см. README).

## 3. Данные и база знаний

- Датасеты: Jena Climate (10-мин, ~14 признаков), `sumanthvrao/daily-climate-time-series-data`
  (дневной, 4 признака + лаги/календарь до ≥5), Monash (weather).
- Признаки ≥5 на датасет: лаги, скользящие статистики, календарные; число признаков — в отчёте.
- Тестовый набор (например, 200 отрезков Jena/daily-climate) не пересекается с базой знаний.
- Расширяемость на табличные задачи: `task_type`, `target_column`, мета-фильтры в Qdrant
  (`task_type`, `num_features`, `problem_type`, `missing_rate`).

## 4. Метрики

- Точность: MAE, RMSE, MAPE, MASE, WAPE; бейзлайн — наивный сезонный прогноз.
- Диагностика остатков: Ljung-Box, Shapiro-Wilk, ACF/PACF.
- Сравнение моделей (обязательно в отчёте): Diebold-Mariano, Wilcoxon signed-rank, bootstrap-CI.
- Агентные: итерации Supervisor, доля HITL, время, токены LLM (из reasoning_logs / llm_calls).
- Подвыборки 10/20/50/100% → кривая «точность vs объём данных».

## 9. Риски и запасные варианты

| Риск | Митигция |
|---|---|
| Prophet/pmdarima плохо ставятся на Windows | ставить через `poetry install` в свежее окружие; при проблемах — WSL2 (как в референс-проекте) |
| Слабая LLM ломает JSON Tool Calling | fallback: 3 попытки → SARIMA(auto_arima) (уже в плане Этапа 7) |
| Нет RAM для Qwen2.5-7B локально | LM Studio/Ollama с меньшей моделью для Critic, Qwen — через OpenRouter (api-провайдер) |
| Qdrant тяжёл для ноутбуков | локально FAISS/Chroma (по заданию), Qdrant — в Docker для prod |
| Сроки (15 этапов) | сдвоенные недели на 9–13; бонусы — в конце |
